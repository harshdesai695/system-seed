# 🎯 What are Message Queues?

**Message Queues** are a communication mechanism that allows different parts of a system to exchange information asynchronously. Instead of talking directly, services drop messages into a queue, and other services pick them up when ready.

<Callout type="tip" title="Real-World Analogy">
  Think of a **restaurant kitchen**. Waiters don't cook food themselves — they write orders on tickets and place them on a **ticket rail** (the queue). Cooks pick up tickets when they're ready. The waiter doesn't wait in the kitchen; they go serve other tables. If a cook is busy, tickets just stack up and are processed in order.
</Callout>

---

## 🌍 Real-World Example

**Uber** uses **Apache Kafka** to handle millions of events per second. When a rider requests a ride, the event goes into a message queue. Multiple services consume from this queue: one matches drivers, another calculates pricing, another tracks analytics — all independently and at their own pace.

---

## 🔍 How Does It Work?

### Core Components

| Component | Role | Analogy |
|-----------|------|---------|
| **Producer** | Creates and sends messages | Waiter placing orders |
| **Queue/Topic** | Stores messages in order | The ticket rail |
| **Consumer** | Reads and processes messages | Cook picking up tickets |
| **Broker** | Manages queues and delivery | The kitchen manager |

### Message Flow

1. **Producer** creates a message (e.g., "new order placed")
2. Message is sent to the **broker** (Kafka, RabbitMQ)
3. Broker stores the message in the appropriate **queue/topic**
4. **Consumer** pulls the message and processes it
5. Consumer **acknowledges** successful processing

## 📊 Queue vs Topic (Pub/Sub)

| Feature | Queue (Point-to-Point) | Topic (Pub/Sub) |
|---------|:---:|:---:|
| Consumers | One consumer gets each message | All subscribers get each message |
| Use case | Task distribution | Event broadcasting |
| Example | Processing orders | Notifying multiple services |

## 💻 Code Example: Producer & Consumer

  title="Message Queue Pattern"
  java={`// Simple in-memory message queue
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.LinkedBlockingQueue;

public class MessageQueue<T> {
    private final BlockingQueue<T> queue = new LinkedBlockingQueue<>();

    // Producer: Add message to queue
    public void publish(T message) {
        queue.offer(message);
        System.out.println("Published: " + message);
    }

    // Consumer: Take message from queue (blocks until available)
    public T consume() throws InterruptedException {
        T message = queue.take();
        System.out.println("Consumed: " + message);
        return message;
    }

    public int size() { return queue.size(); }
}

// Usage with producer and consumer threads
MessageQueue<String> queue = new MessageQueue<>();

// Producer thread
new Thread(() -> {
    queue.publish("Order #1001");
    queue.publish("Order #1002");
}).start();

// Consumer thread
new Thread(() -> {
    while (true) {
        String order = queue.consume();
        processOrder(order);
    }
}).start();`}

import time

class MessageQueue:
    def __init__(self):
        self._queue = queue.Queue()

  go={`type MessageQueue struct {
    messages chan string
}

func NewMessageQueue(bufferSize int) *MessageQueue {
    return &MessageQueue{messages: make(chan string, bufferSize)}
}

// Producer
func (mq *MessageQueue) Publish(message string) {
    mq.messages <- message
    fmt.Printf("Published: %s\\n", message)
}

// Consumer
func (mq *MessageQueue) Consume() string {
    msg := <-mq.messages // Blocks until available
    fmt.Printf("Consumed: %s\\n", msg)
    return msg
}

// Usage
func main() {
    mq := NewMessageQueue(100)

    // Producer goroutine
    go func() {
        for i := 0; i < 5; i++ {
            mq.Publish(fmt.Sprintf("Order #%d", 1001+i))
        }
    }()

    // Consumer goroutine
    go func() {
        for {
            order := mq.Consume()
            fmt.Printf("Processing: %s\\n", order)
        }
    }()
}`}
  cpp={`#include <queue>
#include <mutex>
#include <condition_variable>
#include <string>

class MessageQueue {
    std::queue<std::string> queue;
    std::mutex mu;
    std::condition_variable cv;

public:
    void publish(const std::string& message) {
        std::lock_guard<std::mutex> lock(mu);
        queue.push(message);
        cv.notify_one();
        std::cout << "Published: " << message << std::endl;
    }

    std::string consume() {
        std::unique_lock<std::mutex> lock(mu);
        cv.wait(lock, [this] { return !queue.empty(); });
        std::string msg = queue.front();
        queue.pop();
        std::cout << "Consumed: " << msg << std::endl;
        return msg;
    }
};`}

## 📊 Popular Message Queues Compared

| Feature | Kafka | RabbitMQ | Amazon SQS |
|---------|:---:|:---:|:---:|
| **Throughput** | Millions/sec | Thousands/sec | Thousands/sec |
| **Persistence** | Disk (log-based) | Memory + Disk | Cloud managed |
| **Ordering** | Per partition | Per queue | Best effort |
| **Replay** | Yes (consumers can re-read) | No (message deleted after ack) | No |
| **Best for** | Event streaming, logs | Task queues, routing | Simple cloud queues |

## ⚖️ Pros & Cons

| Pros ✅ | Cons ❌ |
|---------|---------|
| Decouples services | Added complexity |
| Handles traffic spikes (buffering) | Message ordering challenges |
| Retry on failure | Potential message duplication |
| Async processing | Debugging is harder |
| Scalable independently | Latency (not real-time) |

---

## 🧩 When to Use / When NOT to Use

**Use message queues when:**
- Services need to communicate asynchronously
- You need to handle traffic spikes (buffer requests)
- Tasks can be processed with some delay (email sending, image processing)
- You want to decouple services for independent scaling

**Don't use when:**
- You need synchronous, real-time responses
- The system is simple enough for direct API calls
- Message ordering is critical and hard to guarantee
