# 🎯 What is Database Replication?

**Database Replication** is the process of keeping copies of the same data on multiple database servers. When one server gets the data, it's automatically copied to the others.

<Callout type="tip" title="Real-World Analogy">
  Imagine a teacher writing notes on a whiteboard. Three students (replicas) each copy the notes into their own notebooks. If one student is absent, the other two still have the notes. If many students need to read the notes, they can read from any of the three notebooks instead of crowding around the whiteboard.
</Callout>

---

## 🌍 Real-World Example

**Netflix** uses database replication across multiple AWS regions. When you add a movie to your watchlist in New York, that data is replicated to servers in London and Tokyo. This means your watchlist loads fast no matter where you are, and if one region goes down, others keep serving your data.

---

## 🔍 How Does It Work?

### Master-Slave (Primary-Replica) Replication

The most common approach:

- **Master (Primary)**: Handles all **writes** (INSERT, UPDATE, DELETE)
- **Slaves (Replicas)**: Handle **reads** (SELECT queries)
- Data flows **one way**: Master → Slaves

| Component | Role | Handles |
|-----------|------|---------|
| Master | Single source of truth | All writes |
| Slave 1 | Read replica | Read queries |
| Slave 2 | Read replica | Read queries |
| Slave 3 | Read replica + backup | Read queries |

### Master-Master (Multi-Primary) Replication

Both servers can handle reads AND writes:

- **Master 1** and **Master 2** both accept writes
- Changes are synced bidirectionally
- Risk of **write conflicts** when both modify the same data

---

## 📊 Replication Strategies

| Strategy | How it works | Consistency | Performance |
|----------|-------------|:-----------:|:-----------:|
| **Synchronous** | Master waits for all replicas to confirm | Strong | Slower |
| **Asynchronous** | Master doesn't wait; replicas sync later | Eventual | Fast |
| **Semi-synchronous** | Master waits for at least one replica | Good balance | Medium |


---

## ⚖️ Pros & Cons

| Pros ✅ | Cons ❌ |
|---------|---------|
| High availability (failover) | Replication lag (stale reads) |
| Read scalability | Write bottleneck (single master) |
| Data redundancy / backups | Complexity in conflict resolution |
| Geographic distribution | Storage cost (multiple copies) |

---

## 🧩 When to Use / When NOT to Use

**Use replication when:**
- Your application is read-heavy (read:write ratio > 10:1)
- You need high availability and automatic failover
- Users are distributed across regions
- You need real-time backups

**Don't rely solely on replication when:**
- You have a write-heavy workload (consider sharding)
- You need strict immediate consistency
- Storage cost is a major concern
