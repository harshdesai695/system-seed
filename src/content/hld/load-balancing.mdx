# 🎯 What is Load Balancing?

**Load Balancing** is the process of distributing incoming network traffic across multiple servers so that no single server bears too much demand.

<Callout type="tip" title="Real-World Analogy">
  Think of a **restaurant host** who seats guests across all available tables. Without a host, everyone would crowd at the first table while other tables sit empty. The host ensures every table gets a fair share of diners — that's exactly what a load balancer does for servers.
</Callout>

---

## 🌍 Real-World Example

**Uber** handles millions of ride requests every day. When you open the Uber app, your request doesn't go to a single server. Instead, **load balancers** route your request to one of thousands of backend servers. During surge hours (like New Year's Eve), Uber's load balancers distribute the traffic surge evenly so the app stays responsive for everyone.

---

## 🔍 How Does It Work?

A load balancer sits between clients (users) and servers. When a request arrives:

1. **Client** sends a request (e.g., open a webpage)
2. **Load Balancer** receives the request
3. **Load Balancer** picks a server using an algorithm
4. **Server** processes the request and sends the response back
5. **Load Balancer** forwards the response to the client

The client never knows which server handled their request — it's all transparent.

## 📊 Load Balancing Algorithms

### 1. Round Robin
Distributes requests **one by one** in circular order.

| Request # | Server |
|:---------:|:------:|
| 1 | Server A |
| 2 | Server B |
| 3 | Server C |
| 4 | Server A |
| 5 | Server B |

**Best for:** Servers with equal capacity, stateless applications.

### 2. Least Connections
Sends the request to the server with the **fewest active connections**.

**Best for:** When requests have varying processing times (some take 1ms, others take 5s).

### 3. IP Hash
Uses the client's **IP address** to determine which server handles the request. The same client always goes to the same server.

**Best for:** When you need session persistence (sticky sessions) — e.g., shopping carts.

### 4. Weighted Round Robin
Like Round Robin, but some servers get **more requests** based on their capacity.

| Server | Weight | Share |
|--------|:------:|:-----:|
| Server A (powerful) | 5 | 50% |
| Server B (medium) | 3 | 30% |
| Server C (small) | 2 | 20% |

## 📊 Types of Load Balancers

| Type | Layer | What it inspects | Speed | Use Case |
|------|:-----:|:---:|:---:|-----|
| **L4 (Transport)** | TCP/UDP | IP + Port | Very fast | Raw TCP traffic, gaming, streaming |
| **L7 (Application)** | HTTP | URL, headers, cookies | Slower but smarter | Web apps, API routing, content-based routing |

### Layer 4 vs Layer 7
- **Layer 4** just looks at the envelope (IP addresses and ports). It's fast but can't read what's inside.
- **Layer 7** opens the envelope and reads the letter (HTTP headers, URLs, cookies). It can make smarter decisions like routing `/api/*` to API servers and `/images/*` to media servers.

## ⚖️ Pros & Cons

| Pros ✅ | Cons ❌ |
|---------|---------|
| Prevents server overload | Adds network latency (extra hop) |
| Improves availability | Load balancer itself can fail (single point of failure) |
| Enables horizontal scaling | Configuration complexity |
| Health checks remove bad servers | Session management challenges |
| Can terminate SSL centrally | Cost of hardware/software LB |

---

## 🧩 When to Use / When NOT to Use

**Use load balancing when:**
- You have multiple servers to distribute traffic
- You need high availability and fault tolerance
- Traffic is unpredictable or has spikes
- You want zero-downtime deployments

**Don't need load balancing when:**
- You have a single server handling minimal traffic
- Your application is internally scaled (e.g., single powerful machine)
- Traffic is predictable and low volume
