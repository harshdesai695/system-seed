# 🎯 What is Event-Driven Architecture?

**Event-Driven Architecture (EDA)** is a design pattern where the flow of the program is determined by **events** — significant changes in state. Components produce, detect, and react to events asynchronously, enabling loose coupling and high scalability.

<Callout type="tip" title="Real-World Analogy">
  Think of a **newspaper subscription**. The publisher doesn't call every subscriber when news breaks. Instead, they publish the newspaper (emit an event), and all subscribers receive it independently. Subscribers can join or leave without the publisher knowing.
</Callout>

---

## 🌍 Real-World Example

**Uber** uses EDA extensively. When a rider requests a ride, an event is emitted. Multiple services react independently: the matching service finds a driver, the pricing service calculates fare, the notification service alerts the driver, and the analytics service logs the request — all triggered by one event.

### 1. Event Notification
Producer emits an event; consumers react. No response expected.

### 2. Event-Carried State Transfer
Events carry enough data for consumers to update their own state without querying back.

### 3. Event Sourcing
Store every state change as an immutable event. Current state = replay all events.

### 4. CQRS (Command Query Responsibility Segregation)
Separate write operations (commands) from read operations (queries) using different models.

## 📊 Architecture Comparison

| Pattern | Coupling | Throughput | Complexity | Data Consistency |
|---------|----------|-----------|------------|-----------------|
| **Request-Response** | Tight | Lower | Low | Strong |
| **Event-Driven** | Loose | High | Medium | Eventual |
| **Event Sourcing** | Loose | High | High | Event-based |
| **CQRS + Events** | Loose | Very High | Very High | Eventual |


---

## ⚖️ Pros & Cons

| Pros ✅ | Cons ❌ |
|---------|---------|
| Loose coupling between services | Harder to debug/trace |
| Highly scalable | Eventual consistency challenges |
| Easy to add new consumers | Event ordering can be tricky |
| Natural audit trail (event store) | Requires infrastructure (message brokers) |

---

## 🧩 When to Use

- **Use when:** Microservices need to react independently, real-time processing, audit trails, high throughput systems
- **Avoid when:** Strong consistency is required, simple CRUD applications, team lacks experience with async systems

## 📝 Quick Quiz

**Q1: In an e-commerce system, when an order is placed, inventory, email, and billing need to update. What approach minimizes coupling?**

A) Order service calls each service directly  B) Order service publishes an event; each service subscribes

**Answer: B** — Event-driven design lets each service react independently. Adding new consumers (e.g., analytics) requires zero changes to the order service.
